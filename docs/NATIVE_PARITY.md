# Native engine parity

How the native engine ([architecture](NATIVE_ENGINE.md)) is held to llama.cpp
at the pinned commit (`b1b770d9`, vendored in `Sources/LlamaCpp`): the fixed
prompt set, the goldens captured from llama.cpp, and how a backend or a single
component is compared with them.

generated by [`Scripts/native/golden/make_prompt_set.py`](../Scripts/native/golden/make_prompt_set.py)

## Goldens

### Capture

[`Scripts/native/golden/mfe_golden.cpp`](../Scripts/native/golden/mfe_golden.cpp)
links the pinned llama.cpp built from the upstream checkout by
[`Scripts/native/llama/Makefile`](../Scripts/native/llama/Makefile) (no cmake;
Metal and CPU backends with the vendored target's defines). The vendored
`Sources/LlamaCpp` tree is byte-identical to that checkout
(`Sources/LlamaCpp/vendoring/vendor.sh <checkout> --check`), so the tool
needs no change to the vendored sources: the per-op dump is llama.cpp's own
eval callback (`llama_context_params.cb_eval`, a
`ggml_backend_sched_eval_callback`).

For each prompt the tool runs two passes in one process:

1. **Pass A, the golden.** The product's `LlamaBackend` settings: every layer
   on Metal, `n_batch` 2048, `n_ubatch` 512, F16 KV, flash attention auto,
   `n_seq_max` 1. Prefill, then greedy decode one token per step (argmax,
   ties to the lowest id) until an end-of-generation token or `max_new`.
   The F32 logits row behind every choice is kept: `logits.f32`
   `[n_gen x 248320]`, row `g` at position `n_prompt - 1 + g`.
2. **Pass B, per-op tensors.** A fresh sequence: the prompt in 512-token
   chunks (the same ubatch boundaries as pass A), then pass A's tokens
   teacher-forced one per decode step. The callback copies named graph
   tensors at the selected positions (`capture` in the prompt set: the first
   `head` rows, the last `tail` rows, every `stride`-th row, all rows for the
   short prompts) and at the first `decode_steps` decode steps. Logits are
   requested for exactly the selected rows, so the last block (which llama.cpp
   crops to output rows) is captured at the same positions.

Pass B's decode-step logits are bit-identical to pass A's. Its prompt-row
logits come from a step with several output rows instead of one, so its last
block runs a different kernel shape: on `short-chat` the last prompt row
differs from pass A by at most 0.004 in a logit (KL 1.4e-10). Compare
per-op tensors with pass B and logits with pass A.

Build it from a clean checkout at the pin (`LL`) into a directory outside the
repository (`OUT`):

```bash
make -f Scripts/native/llama/Makefile LL=<llama.cpp> OUT=<build> -j8 all
```

Run it as one model command under the machine lock.
[`Scripts/native/guarded-run.sh`](../Scripts/native/guarded-run.sh) refuses
without a passing `lock.sh preflight` or the GGUF, or with another model
process running. It stops the command and exits 70 on any swap growth, and it
records the power source, swap at start and end, wall time and peak footprint
in `<log-dir>/run.json`. Capture and parity runs may run on battery. Timing
runs pass `--timing`, which refuses unless on AC power
(the benchmark protocol):

```bash
export LOCK=<program>/lock.sh GGML_METAL_PATH_RESOURCES=<llama.cpp>/ggml/src/ggml-metal
$LOCK run --wait 3600 ws2 "mfe golden" -- Scripts/native/guarded-run.sh <log-dir> <gguf> -- \
  <build>/mfe-golden --model <gguf> --prompts Tests/Mference/Fixtures/native/prompts/quick-v1.json \
  --out <goldens>/quick-v1/metal --mode golden --backend metal
```

`--mode logits` skips pass B; `--teacher <run>` feeds that run's tokens at
every step instead of the step's own argmax (teacher forcing, for runs compared
with the golden position by position; each step's own argmax is kept as
`argmax_tokens`); `--backend cpu` runs every layer on the CPU backend;
`--batch`/`--ubatch`, `--kv`, `--fa`, `--sel`/`--all`/`--state` change the
settings and the captured names.

### Where they live

Goldens are large and are not committed. The program keeps them under
`scratch/mference-engine-program/goldens/quick-v1/<run>/<prompt-id>/`:

| Run | What |
|---|---|
| `metal` | **The golden.** Pass A and pass B as above. Re-captured from a clean tools build and byte-identical. |
| `metal-rerun` | Noise floor: the same settings again, teacher-forced on `metal` (`--mode logits`). |
| `metal-ub128` | Noise floor: `n_ubatch` 128. |
| `metal-fa-off` | Noise floor: flash attention off. |
| `cpu` | Noise floor: every layer on llama.cpp's CPU backend (`--mode golden`, `--threads 8`), per-op tensors included. |

The committed digest
[`Tests/Mference/Fixtures/native/goldens/quick-v1-metal-slice.json`](../Tests/Mference/Fixtures/native/goldens/quick-v1-metal-slice.json)
([`make_slice.py`](../Scripts/native/golden/make_slice.py)) holds, per
prompt, the token count and hashes, the greedy tokens, the top-8 logits and
log-sum-exp of every logits row, and the SHA-256 of every golden file. It
pins the goldens and gives model-free tests real llama.cpp numbers.

### Format `mfe-golden-v1`

Each prompt directory holds `golden.json`, `prompt.txt`, `logits.f32` and
`tensors/<key>.f32`. Every `.f32` file is row-major little-endian F32
`[rows x cols]`; row `i` is the value at the `i`-th position of the entry's
`position_ranges` (half-open `[start, end)` ranges, ascending).

| `golden.json` key | Meaning |
|---|---|
| `format`, `prompt_id`, `prompt_set`, `mode` | `mfe-golden-v1`; the prompt; `golden` or `logits` |
| `source` | llama.cpp commit, backend, model, `n_batch`, `n_ubatch`, KV type, flash attention, `n_ctx` |
| `enable_thinking`, `rendered_prompt_file` | template switch; `prompt.txt` |
| `n_vocab`, `prompt_tokens`, `generated_tokens`, `stopped_on_eog` | tokens of pass A |
| `logits` | `{file, rows, cols, position_ranges}` of pass A |
| `capture` | chunk size, selected positions, decode steps, state steps |
| `timing_s` | wall times of the passes; indicative only, never a baseline (goldens captured before the fix that synchronizes after prefill record a near-zero `prefill`) |
| `tensors[]` | `{key, name, base, layer, occurrence, op, ne, cols, rows, position_ranges, file}` |

`name` is the llama.cpp callback name (`<base>-<layer>`, or `<base>` for the
graph-wide tensors); `occurrence` counts graph nodes of that name in one
step (`key` gets a `.k` suffix for `k > 0`); `ne` is the ggml shape at the
first capture; `cols` is the size of one position's row.

The Swift loader is
[`Tests/Mference/Core/Native/Harness/GoldenStore.swift`](../Tests/Mference/Core/Native/Harness/GoldenStore.swift):
`GoldenStore.open(id)` returns a `GoldenPrompt` (manifest, tokens,
`renderedPrompt()`, `logits()`, `tensor(named:occurrence:)`,
`tensor(for: TapPoint, config:)`, `tensor(_ boundary:, layer:)`), and every
matrix is memory-mapped (`GoldenMatrix.row(atPosition:)`,
`withRow(_:_:)`). Tests that read goldens are gated on
`MFERENCE_NATIVE_GOLDENS`, the run directory:

```bash
MFERENCE_NATIVE_GOLDENS=<program>/goldens/quick-v1/metal Scripts/test.sh --filter GoldenStore
```

### Tap points and op boundaries

Each `Native.TapPoint` is compared with the `qwen35` graph tensor
(`src/models/qwen35.cpp` at the pin) below. All are F32 `[positions x cols]`.

| `TapPoint` | llama.cpp tensor | cols |
|---|---|---|
| `embedding` | `model.input_embed` (get_rows of `token_embd`) | 2560 |
| `mixerInput(l)` | `attn_norm-l` | 2560 |
| `mixerOutput(l)`, full attention | `attn_output-l` (after `attn_output`) | 2560 |
| `mixerOutput(l)`, GDN | `linear_attn_out-l` (after `ssm_out`) | 2560 |
| `ffnOutput(l)` | `ffn_out-l` (after `ffn_down`) | 2560 |
| `layerOutput(l)` | `l_out-l` | 2560 |
| `finalNorm` | `result_norm` | 2560 |
| `logits` | `result_output` | 248320 |

In a GDN block `attn_output-l` is the raw delta-rule output (before the gated
norm), not the mixer output; use `linear_attn_out-l`.

Op boundaries, for component tests that feed a contract op the golden inputs
and compare its output (`GoldenTapMap.Boundary`):

| Boundary | llama.cpp tensor | cols | Notes |
|---|---|---|---|
| `attentionQGate` | `Qcur_full-l` | 8192 | `attn_q · h`, per head q then gate |
| `attentionK`, `attentionV` | `Kcur-l`, `Vcur-l` (occurrence 0) | 1024 | raw projections; occurrence 1 of `Kcur` is after norm and RoPE |
| `attentionOutput` | `attn_gated-l` | 4096 | `AttentionOp` output, input of `attn_output` |
| `gdnQKV`, `gdnZ` | `linear_attn_qkv_mixed-l`, `z-l` | 8192, 4096 | |
| `gdnAlpha`, `gdnBeta` | `alpha-l`, `beta-l` | 32 | projections before softplus / sigmoid |
| `gdnOutput` | `final_output-l` | 4096 | `GDNOp` output, input of `ssm_out` |
| `gdnConvState` | `conv_states-l` | 24576 | first decode step only: conv tail before the step, ggml `ne [3, 8192]`, so `[8192][3]` with index `c*3 + k` |
| `gdnState` | `state_predelta-l` | 524288 | first decode step only: S before the step, ggml `ne [128, 128, 32]`; head `h`, element `h*16384 + j*128 + i` is `S[i][j]` (key `i`, value `j`) |
| `ffnInput` | `attn_post_norm-l` | 2560 | |
| `ffnGate`, `ffnUp`, `ffnSwiGLU` | `ffn_gate-l`, `ffn_up-l`, `ffn_swiglu-l` | 9216 | |
| `ffnDown` | `ffn_out-l` | 2560 | |

Layouts against `RecurrentLayout` (conv tail `[convKernel - 1][convChannels]`,
then S `[valueHeads][valueDim][keyDim]`):
- **conv needs a transpose.** The golden is ggml's `[channels][taps]`, the
  layout `[taps][channels]`. `GoldenPrompt.convState(layer:position:)` returns
  it transposed.
- **S needs none.** ggml's element `h*16384 + j*128 + i` is already the
  layout's `[h][j][i]`. `GoldenPrompt.ssmState(layer:position:)` returns it as
  stored.

Together the decode-step state goldens let a GDN decode step at 512, 4K or
32K context be tested on its own: start from `convState` / `ssmState` at
`n_prompt`, feed the step's `gdnQKV`, `gdnZ`, `gdnAlpha`, `gdnBeta`, and
compare `gdnOutput`.

## The bar (D1)

A native backend (or the all-reference path, or a path with one fast
component swapped in) passes against the Metal golden when, over every
generated position of the fixed prompt set, teacher-forced on the golden
tokens:

| Check | Bar | Set by |
|---|---|---|
| Greedy agreement: the candidate's argmax equals the golden token | ≥ 99% of 2,354 positions | D1 (maintainer) |
| Per-token KL(golden ‖ candidate) of the logits, every position | ≤ ε = 0.01 nats | this page |
| Mean per-token KL over the set | ≤ 0.001 nats | this page; an extra gate beyond D1, **pending maintainer sign-off** at the Phase 0 exit |
| Agentic parity (`agentic-v1`) | at most 1 of 32 tasks regresses (golden passes, candidate fails); no setup errors | this page |

Teacher forcing: the candidate prefills the prompt, then is fed the golden's
generated tokens one per decode step; row `g` of its logits is compared with
the golden's row `g`. Agreement and KL therefore never compound after a
disagreement. Each disagreement is reported with the golden's top-1 minus
top-2 logit margin, so near-ties are visible.

Inside Mference the rule stays byte identity (a change against its own
control, a speculative path against plain greedy decode); this bar is only
for a native backend against llama.cpp.

### Metrics

[`ParityMetrics`](../Tests/Mference/Core/Native/Harness/ParityMetrics.swift)
computes log-softmax in F64 from the F32 logits (Accelerate), KL as
`sum p (log p - log q)` with P the golden, argmax with ties to the lowest id
(as `mfe-golden` and llama.cpp's greedy sampler choose), and element-wise
error statistics (max and mean absolute error, relative L2 `‖c - g‖ / ‖g‖`).
[`ParityHarness`](../Tests/Mference/Core/Native/Harness/ParityHarness.swift)
runs them over a golden: `compareLogits(golden:candidate:)` takes a closure
returning the candidate's logits row `g`; `compareTensor(_:candidate:)` takes
the candidate's row at a position for any golden tensor;
`LogitReport.verdict()` applies the bar
([`ParityTolerances`](../Tests/Mference/Core/Native/Harness/ParityTolerances.swift)).

```swift
let golden = try GoldenStore.open("doc-4k")
let result = try ParityHarness.compareLogits(golden: golden) { g in myBackendLogits(row: g) }
let report = ParityHarness.LogitReport(results: [result /*, every prompt */])
#expect(report.verdict().passed, "\(report.verdict().failures)")
```

## ε and tolerances

llama.cpp's own noise floor sets them. Each noise run is teacher-forced on
the golden, so every position compares like for like. All runs are on the
M1 Max, at b1b770d9, over 2,354 positions. KL is in nats, per token.

| Run | Agreement | Mean KL | p99 KL | Max KL | Under the bar |
|---|---:|---:|---:|---:|---|
| `metal-rerun` | 100% | 0 (bit-identical) | 0 | 0 | passes |
| `metal-ub128` | 100% | 0 (bit-identical) | 0 | 0 | passes |
| `metal-fa-off` | 99.96% (1 flip) | 1.9e-7 | 2.0e-6 | 5.8e-6 | passes |
| `cpu` | 98.17% (43 flips) | 2.4e-3 | 1.7e-2 | 0.29 | **fails** (agreement, max, mean) |

llama.cpp on Metal is deterministic: the rerun and the ubatch change are bit
for bit identical. A different attention kernel moves the logits by at most
6e-6. The CPU backend quantizes activations to Q8_K for its dot products,
which is a much larger perturbation. It flips 43 greedy choices, all at
near-ties where the golden's top-1/top-2 logit margin is under 0.28. 42 of
them fall in the four 512-token continuations, where small differences
compound. llama.cpp's own CPU backend therefore does not meet D1 on this set.
A native engine must stay much closer to ggml-metal's numerics, as the Metal
variants do.

- **ε = 0.01 nats per token, and a mean of at most 0.001.** ε is more
  than 1,000 times the Metal configuration noise, which leaves room for
  another accumulation order, F32 versus half staging, and different kernel
  tiling. It is below the CPU backend's p99 (1.7e-2), so a path as far from
  ggml-metal as the CPU backend fails. `ParityNoiseFloorTests` asserts both
  directions (the Metal runs pass, the CPU run fails); if that ever changes,
  ε is revisited. The mean-KL check is an extra gate beyond D1's "per-token
  KL ≤ ε" and is **pending maintainer sign-off**.

### Per-op bounds

A component fed the golden's inputs at an op boundary must match the golden
output within its class's relative L2 bound
(`OpToleranceClass.maxLocalRelativeL2`), applied by
`ParityHarness.localVerdict`. `OpToleranceClass.of(_:)` gives the class of a
`TapPoint`, an op boundary or a golden tensor. It returns nil for a name it
does not know: it never guesses. GDN's `attn_output` (a `VIEW`, the
delta-rule output) is `mixer`; full attention's `attn_output` (`MUL_MAT`) is
`gemm`. A fused kernel is held to the loosest contracted op it contains. A
caller whose kernel writes `layerOutput` with the residual add fused into a
GEMM asks for `OpToleranceClass.of(.layerOutput(layer:), fusedGEMM: true)`,
which is `gemm`; an unfused residual add is `glue`.

The bounds are **provisional**. They are chosen so that meeting them makes D1
likely, not from a backend that fails it:

| Class | Ops | Bound |
|---|---|---:|
| `exact` | embedding (`get_rows`) | 1e-6 |
| `norm` | RMSNorms | 1e-5 |
| `gemm` | every quantized projection, FFN, LM head | 2e-2 |
| `mixer` | attention and GDN core (`attn_gated`, `final_output`, GDN `attn_output`) | 2e-3 |
| `glue` | residual adds, SwiGLU, copies | 1e-5 |
| `state` | GDN conv and S state after a step | 2e-3 |

The bounds come from measured data:
- **gemm (2e-2): set from an implementation that passes D1.** R's naive
  reference (`Native/Reference`) passes D1 on 10 prompts: 99.69% agreement,
  max per-token KL 1.7e-3, mean 5.3e-5. Its local GEMM error against the
  golden, converted to relative L2 from its recorded max and mean errors, is
  largest on `attn_output` and the FFN GEMMs:
  - worst estimate 1.03e-2
  - hard lower bound 8.2e-3
  - loose upper bound 3.2e-2

  2e-2 is about two times the worst estimate, so a reference at that accuracy
  passes, and W2's kernels are not held tighter than a D1-passing path.
- **Local error size alone does not predict D1.** llama.cpp's CPU backend has
  a smaller GEMM error on `attn_qkv` and `attn_gate` (about 4.5e-3, block 0)
  yet fails D1 (98.17%, max KL 0.29). Its error is systematic: Q8_K-quantized
  activations, correlated across every GEMM. The reference's error is
  rounding noise. A bound on local error size is therefore necessary but not
  sufficient; D1 on the logits stays the gate for any path.
- **mixer and state (2e-3) are not derived.** R's attention core is about
  1e-4 and its GDN core about 2e-7, far inside them, so they stay as
  provisional bounds.
- **Confirmation.** Two runs settle the bounds:
  - R's component run records relative L2 in this metric directly, which
    replaces the conversion above. If it shows a D1-passing reference above
    a bound, the bound moves.
  - The perturbation runs measure D1 against random per-op error.
    `mfe-golden --perturb <names|'*'> --perturb-scale s [--perturb-op MUL_MAT]`
    adds Gaussian noise of relative size `s` to the chosen graph tensors in a
    teacher-forced Metal run, before the ops that read them run. The planned
    set covers:
    - every GEMM output at 1e-4, 3e-4, 1e-3 and 3e-3, extended to 1e-2 and
      3e-2 for the new bound
    - the mixer outputs at 1e-3 and 1e-2
    - the norms at 1e-4 and 1e-3

    The bounds become final once each class's bound holds D1 with margin.

Tap points of an end-to-end run carry every earlier block's difference, so
they have no per-op bound. The D1 logits bar is their gate. For scale, the
CPU backend's accumulated difference, pooled over every prompt and position,
is:
- relative L2 0.094 at `l_out` (all blocks)
- 0.14 at `result_norm`
- 0.12 at the logits

Per block, pooled, `l_out` rises steadily from 0.015 at block 0 to 0.114 at
block 31. On `short-chat` alone it is 4.7e-2 to 5.0e-2 at the last block. The
noise-floor report prints the whole per-block profile.

Reproduce (reads files only, no model; about 13 minutes):

```bash
MFERENCE_NATIVE_GOLDENS=<goldens>/quick-v1/metal \
MFERENCE_NATIVE_NOISE_RUNS=<goldens>/quick-v1/metal-rerun:<goldens>/quick-v1/metal-ub128:<goldens>/quick-v1/metal-fa-off:<goldens>/quick-v1/cpu \
MFERENCE_PARITY_REPORT=<file> Scripts/test.sh --filter ParityNoiseFloorTests
```

## Agentic parity

[`Scripts/native/agentic/agentic_parity.py`](../Scripts/native/agentic/agentic_parity.py)
holds `agentic-v1`: 32 tool-use and structured-output tasks:
- choosing among six tools and extracting their arguments (numbers, currency
  codes, dates and 24-hour times, units, paths, recipients)
- knowing when no tool is needed
- using a tool result in the final answer across turns, including a
  follow-up call
- answering in a required JSON shape
- exact short answers

Each task goes to an OpenAI-compatible server on loopback at temperature 0.
A model-free checker scores the parsed tool calls or content: it compares
arguments after normalization, evaluates calculator expressions with a safe
parser, rejects arguments that are not a JSON object, and strips `<think>`
blocks.

Both sides go through the same `MferenceServer` build in `--library` mode:
the golden is the llama.cpp Quick entry (`LlamaBackend` at the pin), the
candidate the native Quick entry. The server renders the chat template and
parses tool calls identically for both, so only the backend differs. A task
whose prompt renders to a different token count on the two sides is a setup
error. It is reported apart (`render_mismatch`), fails the comparison, and is
never counted as a parity result. A request, HTTP or server error on either
side is also a setup error (`setup_errors`): that task measured nothing, so
the comparison fails until it is re-run, and an unreachable golden server can
never certify a candidate.

Parity holds when at most one task regresses (passes on the golden, fails on
the candidate), no task is missing and no prompt rendered differently. Tasks
the candidate newly passes are listed, never counted against it, and never
offset a regression. `run` writes `agentic.json` after every task (`complete`
turns true at the end), and a request error or timeout fails only its own
task. The checker and the verdict are unit-tested without a model
(`Scripts/tests/test_agentic_parity.py`). Real runs are model runs: one server
per lock hold, under the normal server rules.

```bash
python3 Scripts/native/agentic/agentic_parity.py run --port <port> --model <golden-id> --out <dir>/golden
```

```bash
python3 Scripts/native/agentic/agentic_parity.py run --port <port> --model <native-id> --out <dir>/native
```

```bash
python3 Scripts/native/agentic/agentic_parity.py compare <dir>/golden <dir>/native
```

Larger agent benchmarks (Terminal-Bench, SWE-bench) need downloads and an
agent harness. They are held for the maintainer, and this suite does not
replace them.
