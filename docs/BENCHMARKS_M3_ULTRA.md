# Mference benchmark results — Mac Studio M3 Ultra, 256 GB

All four model families supported at the time (Maple landed later) installed,
hash-verified, and benchmarked under the frozen community protocol. Every
measured run reached a natural end of turn (36/36).

## Host

| | |
|---|---|
| Model | Mac Studio `Mac15,14` |
| Chip | Apple M3 Ultra, 32 cores (24 performance, 8 efficiency) |
| Memory | 256 GB |
| Storage free after installs | 3.2 TiB |
| macOS | 26.3 (25D125) |
| Swift | 6.2.4 (swiftlang-6.2.4.1.4), target `arm64-apple-macosx26.0` |
| Mference commit | `282f0b70c2c9a0d34d8e5427dc93c66134a905e7` |
| Build | `swift build -c release` — 103 s, exit 0, all 5 products |

The M3 Ultra GPU is not Apple10, so the shader library compiles at MSL 3.2 and
the non-tensor kernels are selected. The Metal 4 tensor-ops prefill path
described in the README is not exercised by these runs.

## Protocol

The frozen community protocol ([COMMUNITY_BENCHMARKS.md](COMMUNITY_BENCHMARKS.md)): the three
`real-generation-v1` prompts with fixed seeds (20260721 / 20260722 / 20260723),
temperature 0.2, Top-K 64, Top-P 0.95, 4,096-token context, up to 1,024
generated tokens, the runtime defaults at the measured commit (16 expert-cache
slots, prefill on, RDADVISE off), one discarded warmup per case, each measured
run in a fresh process with no other model process running.

Stated deviation: **three** measured repetitions per case instead of one, so
medians and run-to-run spread can be reported. Generated token counts were
identical across repetitions of every case, as expected from the fixed seeds.

Reported by `./run-benchmark.sh <label> <dir> <reps>`; tables regenerated from
the raw per-run stderr by `./summarize-benchmarks.sh`.

## Results

Prefill and decode are both the median of the 3 measured runs; the range column
is the decode min–max, and peak RSS is the maximum across runs. All of it is
generated by `./summarize-benchmarks.sh`, so the published statistic cannot
drift from this description.

As in the existing tables, the file cache was warm but uncontrolled. Cache state
matters more on this host than the tight per-case ranges below suggest: a
one-off Gemma 4 short-explanation run taken later in the session, with the whole
working set resident, reached 24.15 tok/s against the 19.73 median recorded here.
Each table is a measurement of the protocol as run, not a performance ceiling.

### A note on the reported prefill figure

For DeepSeek-V4-Flash and Inkling-Small, the CLI's `prefill=` field includes
the one-time model load. Isolating it:

- DeepSeek-V4-Flash: a 2-token prompt reports `prefill=2tok/35.37s`, giving a
  **~35.4 s** load (mmap + SHA-256 of the 90 GB checkpoint), matching the
  39–43 s the port document records.
- Inkling-Small: solving the two-point system (59 tok → 66.05 s,
  421 tok → 107.21 s) gives a **~59.3 s** load and 0.114 s/token marginal.

The prefill columns above have that load subtracted. This matters: the raw
figure makes short-prompt prefill look catastrophic (11.5 s/token for a
5-token Inkling prompt) when the marginal cost is actually ~0.11 s/token.
Gemma 4 and Qwen 3.6 do not show a comparable fixed term.

## Comparison with published numbers

### Qwen 3.6 — the one strictly comparable table

[BENCHMARKS.md](BENCHMARKS.md)'s Qwen rows use this same protocol, so this is a valid
comparison. (The Gemma 4 reference rows use fixed non-repeating continuations
from a different harness and are **not** comparable to the numbers above.)

| Case | M5, 24 GB | M3 Ultra, 256 GB | Change |
| --- | ---: | ---: | ---: |
| short-explanation | 23.05 tok/s | 22.82 tok/s | −1% |
| medium-review | 21.20 tok/s | 22.19 tok/s | +5% |
| long-synthesis | 18.84 tok/s | 22.18 tok/s | **+18%** |

Level on the short case, pulling ahead as the prompt grows: this host holds
~22.2 tok/s where the M5 decays to 18.84. The published notes attribute the
M5's decay to expert-streaming I/O — Qwen's 18.1 GB expert pool does not fit
that host's page cache. It fits here, which takes the SSD out of the
steady-state decode path.

Peak RSS (1,368–1,384 MiB) is not directly comparable to the published
1,447–1,464 MiB, which are physical footprint rather than RSS.

### DeepSeek-V4-Flash — beats its own port document

| | Doc, M5 24 GB | M3 Ultra, 256 GB |
| --- | ---: | ---: |
| Decode, 16 slots, RDADVISE off | 4.02 tok/s | 5.29–6.06 tok/s |
| Footprint | 5.9 GB | 5.67 GB peak RSS |

~40–50% faster at the same slot count, at slightly lower memory than measured
on M5 and well under the 9.4 GB the budget table allots to 16 slots.

The document's analysis is that decode above ~7 tok/s becomes SSD-limited,
needing 14.2 GB/s of sustained random 8 MB reads, and that reaching that tier
requires ~60% of expert reads served from RAM. Here the entire 90 GB expert
pool fits in page cache after warmup (`vm_stat` showed ~139 GB of cached pages
during the runs), so the ~2.03 GB/token of expert reads is served from memory.
Throughput still sits below the document's ~8–12 tok/s GPU-compute ceiling
estimate, consistent with the then-open roadmap item that expert I/O was not
yet overlapped with GPU work (the DSV4 shadow speculative prefetch has since
landed as that family's default).

### Inkling-Small — beats its estimate

[INKLING_SMALL.md](INKLING_SMALL.md) projects ≈3 tok/s for the selected 4-bit build and
records ≈2.4–6.5 tok/s unoptimized at first light. Measured here:
**5.31–6.92 tok/s**, at the top of that range and above the 3 tok/s projection.

Its 8,936 MiB peak RSS is the largest of the four, consistent with a 3.4 GB
resident set plus 40 layers × 16 slots × 14.16 MB of expert slots.

## Output quality

Every measured output was read. Gemma 4, Qwen 3.6, and DeepSeek-V4-Flash
produced coherent, complete answers with no repetition loops or truncation.

**Inkling-Small has a reproducible token-corruption defect.** Occasional long
or rare words are truncated mid-word and replaced by a burst of exclamation
marks:

```
short-explanation: "Coastal wetlands—salt marshes, mang!!!! Wait, I need to be precise."
medium-review:     "cancellation / ded!!!!:** The executor task ..."
```

Evidence:

- **Deterministic.** All four short-explanation runs (warmup + 3 reps, seed
  20260721) are byte-identical (md5 `cc719d665cfdbf18fcb4bf69db607ead`) and
  each contains exactly one `mang!!!!`.
- **Not a sampling artifact.** It also reproduces under greedy decoding
  (`--temperature 0`), where the argmax token is `!`, and greedy uses a
  different output-head path per [RUNTIME_CONTROLS.md](RUNTIME_CONTROLS.md). The greedy run
  produced two bursts in 120 tokens (`mang!!!!` and `Wet!!!`).
- **Exclusive to Inkling.** 16 `!!` bursts across 10 Inkling output files
  versus **0** across 30 output files from the other three models under the
  identical harness and prompts.
- Absent from the long-synthesis output (312 generated tokens), and absent
  from short raw completions (`--prompt "The capital of France is"` yields
  clean output).

Leading hypothesis: [INKLING_SMALL.md](INKLING_SMALL.md) records that logits must be
truncated to `unpaddedVocabSize` 200,058 of 201,024 "or the model can emit
padding ids that do not decode." A token id landing in the padded region, or an
off-by-one at that boundary, would explain a valid rare subword rendering as
`!`. Worth verifying the truncation is applied on both output-head paths.

The runs do not loop or truncate early, so the throughput numbers above stand;
this is a correctness issue, not a performance one.

## What 256 GB does and does not buy

Footprint held to the documented design targets on every model — 1.84 GB
(Gemma 4), 1.37 GB (Qwen 3.6), 5.67 GB (DeepSeek-V4-Flash), 8.94 GB
(Inkling-Small). The engine keeps its memory budget regardless of host RAM,
exactly as designed. None of these models needs a 256 GB machine to *run*.

The capacity shows up instead as page-cache residency for the streamed expert
pool, and its value scales with pool size:

| Model | Expert pool | Benefit observed |
|---|---:|---|
| Gemma 4 | ~13 GB | none — fits smaller hosts too |
| Qwen 3.6 | 18.1 GB | +18% on long context vs 24 GB M5 |
| DeepSeek-V4-Flash | ~86 GB | +40–50% vs 24 GB M5 |
| Inkling-Small | ~145 GB | not cacheable on any smaller Mac |

The headline is that the two largest models — 284B and 276B total parameters —
run at 5–7 tok/s in under 9 GB of process memory, and this host is the smallest
configuration that can keep their expert pools resident.

## Reproducing

```bash
swift build -c release
.build/release/MferenceRepack --model <gemma4|qwen36|deepseekv4flash|inklingsmall|maple> \
  --output scratch/<name>.gturbo
.build/release/MferenceRepack --verify-install --input-gturbo scratch/<name>.gturbo
./run-benchmark.sh <label> scratch/<name>.gturbo 3
./summarize-benchmarks.sh
```

Both scripts live at the repository root. Each run writes per-case stdout,
stderr, and a `system/system.txt` machine record under
`benchmark-results/<label>/`. That directory is git-ignored as scratch output,
so the raw per-run captures behind the tables above are not tracked in the
repository; regenerate them with the commands above, or attach them to a
benchmark issue as [CONTRIBUTING.md](../CONTRIBUTING.md) describes.
