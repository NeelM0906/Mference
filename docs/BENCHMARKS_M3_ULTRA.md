Qwen 3.6 35B-A3B installed, hash-verified, and benchmarked under the frozen
community protocol. Every measured run reached a natural end of turn. The
sessions also measured families that have since been retired; their rows were
removed with them ([Retired model families](RETIRED_FAMILIES.md)).

## Protocol

The frozen community protocol ([COMMUNITY_BENCHMARKS.md](COMMUNITY_BENCHMARKS.md)): the three
`real-generation-v1` prompts with fixed seeds (20260721 / 20260722 / 20260723),
temperature 0.2, Top-K 64, Top-P 0.95, 4,096-token context, up to 1,024
generated tokens, the runtime defaults at the measured commit (16 expert-cache
slots, prefill on, RDADVISE off), one discarded warmup per case, each measured
run in a fresh process with no other model process running.

Stated deviation: **three** measured repetitions per case instead of one, so
medians and run-to-run spread can be reported. Generated token counts were
identical across repetitions of every case, as expected from the fixed seeds.

Reported by `./run-benchmark.sh <label> <dir> <reps>`; tables regenerated from
the raw per-run stderr by `./summarize-benchmarks.sh`.

## Results

Prefill and decode are both the median of the 3 measured runs; the range column
is the decode min–max, and peak RSS is the maximum across runs. All of it is
generated by `./summarize-benchmarks.sh`, so the published statistic cannot
drift from this description.

As in the existing tables, the file cache was warm but uncontrolled. Cache state
matters more on this host than the tight per-case ranges below suggest. Each
table is a measurement of the protocol as run, not a performance ceiling.

## Comparison with published numbers

### Qwen 3.6 — the one strictly comparable table

[BENCHMARKS.md](BENCHMARKS.md)'s Qwen rows use this same protocol, so this is a valid
comparison.

| Case | M5, 24 GB | M3 Ultra, 256 GB | Change |
| --- | ---: | ---: | ---: |
| short-explanation | 23.05 tok/s | 22.82 tok/s | −1% |
| medium-review | 21.20 tok/s | 22.19 tok/s | +5% |
| long-synthesis | 18.84 tok/s | 22.18 tok/s | **+18%** |

Level on the short case, pulling ahead as the prompt grows: this host holds
~22.2 tok/s where the M5 decays to 18.84. The published notes attribute the
M5's decay to expert-streaming I/O — Qwen's 18.1 GB expert pool does not fit
that host's page cache. It fits here, which takes the SSD out of the
steady-state decode path.

Peak RSS (1,368–1,384 MiB) is not directly comparable to the published
1,447–1,464 MiB, which are physical footprint rather than RSS.

## Output quality

Every measured output was read. Qwen 3.6 produced coherent, complete answers
with no repetition loops or truncation.

## What 256 GB does and does not buy

Qwen 3.6's footprint held to its documented design target, 1.37 GB. The
engine keeps its memory budget regardless of host RAM, exactly as designed;
the model does not need a 256 GB machine to *run*.

The capacity shows up instead as page-cache residency for the streamed expert
pool: Qwen 3.6's 18.1 GB pool fits here, worth +18% on long context against
the 24 GB M5.

Same host, 248 commits later — after the Qwen slot-map/96-slot campaign, the
Maple and Qwen 3.8 families, and the Qwen 3.8 paged-KV SSD tier all landed.
Every family installed (or reinstalled) from its pinned revision and
hash-verified with `--verify-install`; Qwen 3.6 was benchmarked under the
same frozen protocol, three measured repetitions per case, every measured run
in a fresh process on an otherwise idle machine. Every measured run reached a
natural end of turn.

Session facts: macOS 26.3 (25D125), Swift 6.2.4 (CommandLineTools),

### Protocol results (medians of 3; ranges are decode min–max)

Prefill is reported raw, as the CLI prints it.

**Qwen 3.6 35B-A3B** — auto now selects the 96-slot rung on this host (the

| Case | Prompt / generated | Prefill | Decode | Range | Peak RSS | vs 16-slot session |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| short-explanation | 62 / 507 | 7.41 s | 42.20 tok/s | 41.55–42.52 | 6,788 MiB | **+85%** |

surfaces keep 16 slots.

### Qwen 3.8 27B (dense) — outside the protocol

The chat template opens a `<think>` block, so under the protocol's 1,024-token
cap no run reaches a natural end of turn and `run-benchmark.sh` correctly
aborts (a warmup measured 36.2 tok/s decode before rejection). Measured by the
family's own documented method instead (`--temperature 0`, 128 new tokens,
fresh processes, raw-completion prompt):

| Configuration | M3 Ultra | M5 24 GB (family docs) |
| --- | ---: | ---: |
| Plain greedy decode | 38.4–39.4 tok/s | 7.9–8.0 |
| MTP speculative, k=3 | 33.7–39.6 tok/s | 15.0–15.1 |
| Paged KV + SSD spill, 10,611-token needle | 26.6 tok/s (dense control 27.1) | 5.9 (7.8) |
| Blocked streamed prefill, same needle | 125 tok/s | 27 |

- MTP attach: `model-00018-of-00018.safetensors` from `Qwen/Qwen3.8-27B`
  (the checkpoint the pinned mlx conversion quantizes), +238,930,944 bytes in
  place, byte-identical greedy output before/after and with `MFERENCE_MTP=0`.
- **MTP gives no speedup on this host.** `MFERENCE_PHASES` confirms the
  drafter works (49 rounds, 53.1% accept, ~2.6 tokens emitted per verify), but
  a verify round costs ≈3× a plain decode step here, cancelling the gain. On
  the bandwidth-starved M5 the same trade is 1.9×; speculation buys back
  memory bandwidth this host does not lack. A host-aware default may be worth
  considering.
- Paged KV with the pool forced to 128 pages/layer (SSD spill active)
  retrieved the passkey exactly and produced output byte-identical to the
  dense control at ~2% decode cost — on the M5 the same scenario cost ~19%.

Maple smoke (protocol short case, seed 20260721): 38.5 tok/s decode, coherent
output, `stop=maxTokens` as expected for a think-block family (16 GB M4 doc:
18.9–24.6 tok/s).

## Reproducing

```bash
swift build -c release
.build/release/MferenceRepack --model <qwen36|qwen38|maple> \
  --output scratch/<name>.gturbo
.build/release/MferenceRepack --verify-install --input-gturbo scratch/<name>.gturbo
./run-benchmark.sh <label> scratch/<name>.gturbo 3
./summarize-benchmarks.sh
```

Both scripts live at the repository root. Each run writes per-case stdout,
stderr, and a `system/system.txt` machine record under
`benchmark-results/<label>/`. That directory is git-ignored as scratch output,
so the raw per-run captures behind the tables above are not tracked in the
repository; regenerate them with the commands above, or attach them to a
benchmark issue as [CONTRIBUTING.md](../CONTRIBUTING.md) describes.
